# Dashboard: the SPA and its routes

How the front-end is built, and the views beyond the schema forms. Moved verbatim from `CLAUDE.md` (P12, D5); its one-line rules point here.

## Custom Web UI views

When schema-driven forms aren't enough (e.g. CRUD over a list of objects, anything that mutates Discord state from the dashboard), drop a router in `src/webui/routes/<name>.py` exposing a `create_router(ctx: WebUIContext) -> APIRouter` factory and register it in `src/webui/app.py` next to the others. `ctx` carries the bot client, the config store, and the auth helpers, so routes can both read MongoDB *and* call back into Discord (post/edit messages, etc.). The reaction-role menu builder (`src/webui/routes/rolemenus.py` paired with `features/reactionroles/`) is the reference pattern; `routes/moderation.py`, `routes/spotify.py` and `routes/secretsanta.py` follow it. A route never returns a whole guild's members: `GET /api/servers/{id}/members` answers one search page (`?q=&limit=&offset=`, 100 at most, with the total) or the few members a form references (`?ids=`), from a list built on the bot loop and kept a minute per guild (`src/webui/members.py`); the SPA's member pickers search through it. Channel pickers get theirs from `src/webui/channels.py`. Keep a route's body short: the work it does on the bot loop goes in a module-level function it hands to `ctx.call_bot` (see `routes/rolemenus.py`), not in a closure inside `create_router`. The frontend is a single SPA with no build step: markup in `src/webui/static/index.html`, styles in `app.css`, and native ES modules under `static/js/` (C8): `core/` (state, `api()`, router, actions, `html`), `ui/` (modal, confirmation, toasts, charts), `forms/` (the schema form, one file per list widget under `forms/widgets/`, the pickers under `forms/pickers/`), `pages/` (one per page or server-page card) and `features/` (role menus, Spotify, XP…). `js/main.js` imports every module (`tests/test_spa_csp.py` checks) and starts the app. A module imports what it uses by a relative, one-line `import … from './x.js';`: `frontend.py` serves `/static/` (scripts and stylesheets of that folder only) and adds `?v=<hash of the static files>` to the page's assets and to each import, so a versioned file is cached for good and a deploy changes every URL; a dynamic `import()` or a bare specifier would skip that, and the test refuses them. `frontend.py` catch-alls any unknown path back to the page, so new views are a new module under `pages/` rather than a per-view template.

## Web UI authorization

- **Live preview and the save bar** (P9, C4 / C5). Under each template field, `.discord-preview` shows its messages as Discord will: `POST …/template-preview` renders them with the same function as the DM test and production (`preview_texts()`, nothing sent or recorded), and `js/ui/discord.js` only draws the result (Markdown, mentions and channels by name, the author line), escaping the text first and cutting links, mentions and code out before any formatting, so no markup reaches an `href`. The preview is a `POST` sent as the admin types: it has its own budget in the mutation limiter (`PREVIEW_RATE_LIMIT`), so typing never spends the one saves need, and it calls `api(…, { quiet: true })` (no toast; it says a failure in place). A box that names a field uses `data-preview-field`, never `data-field`, which a save reads as a form value. While a module form has unsaved edits, a bar at the bottom counts the fields changed (`changedFields` in `js/core/dirty.js`, from each `.form-field[data-key]` edited) with Annuler, Tester and Enregistrer; Ctrl+S (⌘S) saves, blurring the field first so its change lands before the save. Each module save keeps the settings it replaced in `guild_<id>.config_history` (`src/webui/config_history.py`: secret fields left out, no user id, TTL 90 days, purged with the guild), listed by "🕘 Historique" with what each save changed (channels and roles by name, lists counted, never an id); "Restaurer" (`POST …/history/{id}/restore`) is a save through `save_module_settings()` in `routes/servers.py`, the one path every module save takes: the size, channel and role checks, the schema, the current secrets put back (`restore_section`, which refuses an old URL with today's password), the history and the audit (`module.restore`).

- **"Tester" buttons** (C9, `src/webui/routes/checks.py`): "🧪 Tester" on an RSS row reads the feed now through `fetch_untrusted()` and shows its 3 latest entries as the bot would post them (`features/rss/render.py`, shared with the extension), with the row's label and template, saved or not; "🔌 Vérifier la connexion" tries a module's *saved* settings against its service, so a stored secret never leaves the server. A module gets one by an entry in `CHECKS`, only when its client lives outside its extension (a route never imports an extension): LLDAP today. Neither stores, posts or audits anything.

- **Template tests** (`POST …/template-test`, `src/webui/template_tests.py`): the "✉️ Tester en MP" button under a message template sends the form's current texts, unsaved, and the bot DMs the admin each one rendered by the function it uses in production (`fill_message()`, the same as `pick_weighted_message()`; `render_notification()` for YouTube), with the admin standing in for the member, plus warnings for an unknown `{variable}` and an `@everyone`. A new template field gets an entry in `TESTS` with the renderer and variables its extension uses.

- **The SPA reports what really happened.** `api()` (`js/core/api.js`) throws on any failed write, with the server's `detail` made readable (`errorText()` joins FastAPI's validation list), so a caller's success toast only follows a success; a `403` is silent only on a `GET` (a developer-only read). A `401` once logged in keeps the page and shows a banner (`showSessionExpired()`), so unsaved edits survive. Edits to a form (`.schema-form` on a page, the role-menu builder) mark it modified (`setDirty`, the "● Modifié" badge): leaving it asks first (`confirmDiscard()` in `navigate()`, `beforeunload`), and a successful save clears the mark. Every page has a hash route (`routeHash()` / `parseHash()`: `#/server/<id>`, `#/module/<id>/<module>`, `#/logs`…), so links, reloads and the back button work; navigation is a real `<a href>` with `data-click="navigate"` and `data-prevent`. Actions that change the whole bot or publish to Discord (`toggleExtension`, `toggleModule`, `reloadAllExtensions`, `publishEmbeds`) confirm first, with the app's own dialog: `await askConfirm(message, { title, confirm, danger })`, never the browser's `confirm()` (the smoke tests fail on a native dialog). A destructive one passes `danger: true`: a red button, and the focus on "Annuler". A save sends the module's stored settings with the form's values on top, minus the fields the form left empty: emptying a field is how an admin clears it. Colours are tokens in `:root`: the plain `--danger` / `--success` for text and outlines, the `-strong` ones for the fills white text sits on, `--link` for links; `tests/test_spa_contrast.py` holds each text/background pair at WCAG AA (4.5:1) and fails on a `var(--x)` that nothing defines. A field offering a few fixed values is a `choice` (`ui(…, "choice", choices={value: label})`, annotated with the matching `Literal`; `tests/test_module_registry.py` checks the two agree). Field help is the schema's `description`, with `**gras**` and `` `code` `` rendered (`mdInline()`, over escaped text). A page with three cards or more gets a sticky index of them (`buildPageIndex()`). Accessibility: a `<label for=…>` per schema field, an `aria-label` on toggles and icon-only buttons, and the modal is a `role="dialog"` that takes focus, keeps Tab inside and closes on Échap. `tests/test_spa_smoke.py` drives the real app in Chromium (Playwright, marker `browser`, its own CI job; skipped without a browser, `PLAYWRIGHT_CHROMIUM_PATH` points at one), and fails on a script error or a console error (a module that didn't load, an unknown action). A `page.route` faking an API answer names the API path (`**/api/servers/*/audit**`): a bare `**/audit**` also catches `js/pages/audit.js`.

- **The SPA escapes every value it interpolates into HTML.** Guild names, member names and module config values are written by guild admins and members, and are rendered to developers: one unescaped interpolation is stored XSS on the developer's session (the CSP stops injected markup from running script, but not from rewriting the page). New markup is built with the `html` tag (`js/core/html.js`): ``html`<p title="${name}">${text}</p>` `` escapes every value unless it is itself `html`…`` (or an array of them) or `raw(…)`, markup made some other way (a `renderSchemaForm()` string, `mdInline()`), and `false` / `null` / `undefined` render nothing, so `${cond && html`…`}` works (pass `String(flag)` where `false` is the value, as in `aria-pressed`). `actionArgs()` returns `raw()`, escaped once. The result reads as its text wherever a string goes (`innerHTML`, an older `` `…${x}…` ``). Every page now builds its markup this way; the only `escapeHtml(` calls left are the helpers' own, `mdInline()` and the log search marks, and `tests/test_spa_html.py` holds them to a ceiling that only goes down and lists the pages written with `html` only (URL parts still go through `encodeURIComponent()`). A config value that feeds an attribute of a fixed shape (a color) is validated against that shape first.
- **A schema field is rendered and read by its type's entry in `FIELDS`** (`js/forms/fields.js`): `{ render(ctx) → html, collect(el) → value }`, where `ctx` holds the key, value, schema entry and the label's id, and `collect` returns `undefined` to leave the field out of the save. `renderSchemaForm()` (`js/forms/schema-form.js`) only adds the shared frame (label, help, template test and preview) and `collectFormValues()` walks the `[data-field]` elements; a new widget lives in `js/forms/widgets/<name>.js`, exports its `…Field` object and is added to `FIELDS`, never as a new branch in the form. Pickers (`js/forms/pickers/`) export a `…PickerHtml()` and a `…PickerValue()`. Accounts the bot itself uses (`botId`, `ownerId`, `developerUserIds`) are `account` / `accountlist` fields: an id input labelled with the account's name from `GET /api/accounts?ids=` (developer only, 25 ids at most). **No static inline style**: layout uses the `u-*` utility classes at the end of `app.css` (one property each, `!important`, so they win as the `style=` they replaced did) or a named class; `style=` only carries a computed value (a width in %, a role colour). Showing and hiding is the `hidden` attribute (`el.hidden = …`, `[hidden]` is `display: none !important`), never `style.display`, so a class can't override it by accident.
