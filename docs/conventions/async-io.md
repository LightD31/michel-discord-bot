# Async and I/O

Never block the loop; who may be fetched, and how. The one-line rules of `CLAUDE.md` point here.

## Async everywhere

PyMongo async (MongoDB), aiohttp (HTTP), asyncssh (SFTP). Never block the event loop. Outbound connections that carry credentials authenticate the server: the Minecraft SFTP connection trusts only the configured `minecraftSftpHostKey` (`features/minecraft/stats_sftp.py:trusted_host_keys`), LLDAP password changes go over `ldaps://` with a verified certificate, and the Satisfactory API token goes only to the certificate pinned in `satisfactoryServerCertificateSha256` (a dedicated server's certificate is self-signed: `_PinnedAdapter` makes urllib3 check the fingerprint, the status isn't read without one). Use the shared aiohttp session from `src.core.http` rather than creating per-call clients — it adds retry with jittered backoff and redacts credentials from logged URLs.

- **URLs someone else chose go through `fetch_untrusted()`, not `fetch()`.** That covers a guild's RSS feeds, `/rss tester`, the Streamlabs team URL and the API URLs derived from it, pagination links read from such a response, the Speedons API URL and the ZeratoR 24/7 site. The exception is LLDAP, which lives on the bot's private network by design: its admin password is bound to its URLs (`sent_to`, see *Secrets*) instead. `fetch_untrusted()` (`src/core/http.py`) only reaches public addresses: its resolver drops loopback, private, link-local (cloud metadata) and reserved IPs, an IP-literal host is checked before connecting, and every redirect is re-checked. It caps the body at 5 MB and makes one attempt. A refusal raises `BlockedUrlError` (an `HttpError`). `fetch()` stays for the bot's own configured endpoints.

- **Synchronous SDKs run off the loop.** spotipy is blocking (`requests`, with a `time.sleep` on 429), so coroutines call it as `await spotify_for(guild_id).<method>(...)` (`src/integrations/spotify.py`), the server's own account (P36). Every server's calls run on one dedicated worker thread, which keeps them ordered and token refreshes race-free. A server with no app or no connected account raises `SpotifyNotConnected` (a `NotConnected`, `src/core/errors.py`), never spotipy's prompt on stdin, which would hang the worker; its tasks skip it (`ServerData.connected`). Use `run_spotify(fn, ...)` for other blocking Spotify work (the OAuth code exchange), and catch `SPOTIFY_ERRORS`: transport errors are `requests` exceptions, not the builtin `ConnectionError`. `tests/test_spotify_async.py` fails if an extension calls the synchronous `blocking_client()`. Any other blocking library goes through `asyncio.to_thread` the same way, **with a timeout on its requests**: a call that never returns holds a worker thread for good, its `Task` is skipped as "still running" from then on, and the process can't exit (the default executor is joined at shutdown). Satisfactory's `pyfactorybridge` sets none, so its client is built on a session that does (`_build_api()` in `extensions/satisfactory.py`), each call capped by `asyncio.wait_for`. twitchAPI's `EventSubWebsocket.start()` / `stop()` block the calling loop (a `time.sleep` spin until Twitch answers, for ever when it doesn't): the bot uses `BoundedEventSubWebsocket.start_async()` / `stop_async()` (`src/integrations/twitch_eventsub.py`), never the synchronous pair.

- **CPU work runs off the loop too.** Pillow renders (the rank and welcome cards, the Tricount chart, the Minecraft stats table) and the XML parse of a feed (up to the 5 MB cap) go through `asyncio.to_thread`; a render of a few hundred milliseconds on the loop stalls every command and the heartbeat with it.

- **Pollers fetch in parallel, within a bound.** The RSS cycle (`extensions/rss`) groups the due feeds by URL, so a feed several guilds follow is fetched once, fetches `MAX_CONCURRENT_FETCHES` URLs at a time, and skips a cycle while the previous one still runs. A feed that keeps failing is retried less often: its interval doubles with each consecutive failure, up to 6 h (`features/rss/scheduling.py`).

- **Credentials never go in a URL.** Send API keys in a header (YouTube uses `X-Goog-Api-Key`). `HttpError` redacts its URL and message on construction (`src/core/urls.py`) as a backstop, and log lines that print a URL use `redact_url()`.

Background work that isn't an `interactions` `@Task.create` trigger goes through `spawn()` (`src.core.tasks`), never bare `asyncio.create_task(...)`: the loop holds tasks only weakly, so a discarded handle can be garbage-collected mid-await and cancelled with no traceback. `spawn()` keeps the reference until completion and logs whatever the coroutine raised.

Anything that hands work between the bot loop and the Web UI's uvicorn loop has to cross threads explicitly. `asyncio.Queue`, `Future` and friends are not thread-safe — dispatch with `loop.call_soon_threadsafe(...)` (see `src/webui/log_handler.py`) or, for the Web UI calling into the bot, `ctx.run_on_bot_loop(...)`.
