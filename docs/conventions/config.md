# Config and module schemas

How settings are declared, stored and read. Moved verbatim from `CLAUDE.md` (P12, D5); its one-line rules point here.

## Web UI schema (strongly recommended for any new extension)

Any extension that reads from `config["module<Name>"]` should declare a Pydantic schema using the `@register_module(...)` decorator from `src.webui.schemas` (typically in `extensions/<name>/_common.py`, see `extensions/xp/_common.py` for a canonical example). This is what makes the module appear in the dashboard with editable, typed fields, per-server toggles, and validation — without it the only way to configure the extension is hand-editing `config/config.json` and restarting. New global config sections use `@register_section(...)` the same way. After adding or changing schemas, regenerate `config.example.json` with `scripts/generate_config_example.py`. Every number declares its bounds, `ui(..., ge=…, le=…)` (`Field(ge=…, le=…)` in a nested entry): a save outside them is refused with a French message, the dashboard's input carries them as `min` / `max` with an "Entre … et …" hint, and `tests/test_module_registry.py` fails on a number of a module or section without both, or with a default outside them. Code reading the setting still clamps it to the same range (`spam_rule()` in `features/moderation/spam.py`), since `config.json` can be edited by hand: an anti-spam threshold of 1 deleted every message, and a retention of 0 deleted every backup.

The dashboard never asks for or shows a raw id. A channel is a `channel` field, a role a `role` field (a picker of the guild's roles, `GET /api/servers/{id}/role-choices`, which tells for each role why the editor may not pick it for the field's `role_use`, by the save's own rules), a member a `member` field (the member search); several of them are a `channellist` / `rolelist` (chips, named), and a `keyvaluemap` whose side names a role (`role_use`, `role_keys`) or a member (`member_keys=True`) gets the same pickers. `tests/test_module_registry.py` fails on a `list` field named like a list of channels or roles, and `schemas.channel_ids()` / `role_refs()` read the new types, so the save route checks their entries like any other (`channel_ids(lists=False)` for the health card: the channels a list names are ones the bot leaves alone). The SPA shows names for what the server sends as ids (an infraction's member through `/members?ids=`, a bot message's channel, a role in a refusal: `withRoleNames()`).

The extension class also declares the modules it reads: `MODULE_KEYS = ("moduleXp",)` (several when it reads several, like `metrics`; `moduleUtils` is declared by admin, polls and reminders). Nothing scans the sources: the dashboard builds its module → extension map from the *loaded* extensions (`WebUIContext.module_extension_map()`) to know what to reload after a save or toggle, and accepts a module only when its schema is registered — so the module of an extension that isn't loaded is listed as inactive and can't be edited. An extension that takes its config when it loads (single-guild settings turned into constants, state fetched once at startup, commands built from the config) also declares `RELOAD_ON_SAVE = True`, with a comment saying why: a save of its module reloads it. Every other extension reads its config live (see *Config*), so a save that leaves `enabled` alone reloads nothing. `tests/test_module_registry.py` imports every extension and fails when a class doesn't declare `MODULE_KEYS`, declares a module without a schema, names a `module…` key in its files without declaring it, or when a registered schema has no extension (`discord2name` excepted, read on demand). It also fails when an extension without `RELOAD_ON_SAVE` reads a module's settings at import (`MODULE.get(...)` / `.items()` / `.enabled(...)` outside a function); `guild_ids()` is fine there, for command scopes.

Deliberate exceptions that share config instead of registering their own module: `polls` and `reminders` read `moduleUtils` (owned by `admin`). `userinfo` and `random_` have no per-guild config at all.

## Config

All config lives in `config/config.json`: a `config` key for global sections and a `servers` key for per-guild module configs. `src.core.config.config_store` holds it in memory (atomic tempfile-and-replace writes under a lock, subscriber callbacks), and every write goes through it — `ctx.mutate_config` in the dashboard, `config_store.mutate` in the bot — so the bot never reads a stale copy. Never write `CONFIG_PATH` by hand. The bot writes config only when a command changes a setting (`/twitch-planning`); state it accumulates at runtime belongs in MongoDB, not in the config.

Read it through the live accessors, at use time:

- `MODULE = ModuleConfig("moduleXp")` next to the schema (in `_common.py`), then `MODULE.get(guild_id)` (the guild's settings, `{}` where the module is off), `MODULE.enabled(guild_id)`, `MODULE.items()` / `MODULE.guild_ids()` for the guilds where it is on. Each call reads the store, so a dashboard save is seen on the next read without reloading the extension.

- `global_config()` for the global sections (they are never reloaded for: read them at use time where a change should apply without a restart, as YouTube's API key does).

- Command scopes are the one read taken at import, `scopes=guild_scopes(MODULE.guild_ids())`, which is why switching a module on or off reloads its extensions.

- Name the accessor so it doesn't look sensitive to CodeQL (no `secret`, `token`, `birthday`, `password`…): its clear-text logging query taints whatever comes through such a name, so every log line printing a guild id from `BIRTHDAY.guild_ids()` was a high-severity alert. Birthday's accessor is `MODULE`, Secret Santa's `SANTA`; `tests/test_module_registry.py` checks the names.

- A refresher that keeps one persistent message per guild (a status, a schedule) loops over `MODULE.items()` at each run and gets the message from a `GuildMessages` (`src.discord_ext.messages`): fetched or created once per guild, fetched again when the configured channel changes, dropped with `keep_only()` for guilds where the module was switched off.

- **Where a persistent message lives is not config.** Every message the bot posts once and then edits has a *slot* (`"satisfactory"`, `"speedons:live"`, `"vlrgg:team:<name>"`) and a `bot_messages` document in the guild's database (`src/core/message_refs.py`) holding its channel and id. `fetch_or_create_persistent_message(bot, guild_id=…, slot=…, channel_id=…, label=…)` resolves it: from a process-wide cache, else the stored reference when it points into the configured channel, else a new post whose reference it stores (one resolution at a time per slot, so racing refreshes post once). It returns `None` rather than posting when MongoDB can't be read, so an outage never leaves duplicates. `GuildMessages` wraps it for one slot per guild. After a failed edit (the message was deleted, say), call `forget_persistent_message(guild_id, slot)` and the next refresh resolves it again. A schema never declares a message-id field (`tests/test_module_registry.py` checks). The server page of the dashboard lists a guild's slots (`src/webui/routes/bot_messages.py`) with a link and a "Republier" action (`republish_persistent_message`: deletes the bot's message and its reference, so the module's next refresh posts it at the bottom of its channel). The same page has a "Santé" card (`GET /api/servers/{id}/health`, `src/webui/guild_health.py`): every channel the guild's enabled modules point at (the schemas' `channel_ids()`), checked on the bot loop for the rights the bot lacks there (`REQUIRED_PERMISSIONS`), each RSS feed's last error, failures in a row and next poll, and the `Task` runs of the extensions declaring an enabled module (`src/core/health.py`), each under what it does and when it runs (`TASK_LABELS`, `task_schedule()`: a new `Task` gets its French label there, `tests/test_webui_guild_health.py` fails without one). The developers' Extensions page names each extension after the module it registers, read from its sources without importing it (`extension_card()` in `src/webui/routes/extensions.py`); one that registers none gets an entry in `WITHOUT_MODULE`. Keep any other per-guild state in dicts keyed by guild id, and share what several guilds can (one API client per server, one fetch per team or campaign and refresh). Satisfactory, Streamlabs, Speedons, Olympics and Minecraft are the examples; Zunivers keeps the rest of its per-guild state in one dataclass per guild (`GuildState`). Zevent tracks one edition for the whole bot: its settings are the global section `zevent`, rendered once per refresh and published in every enabled guild, each keeping its channel, milestone and record markers and Discord scheduled event (`ZeventGuild`).

- What the accessors return is the store's own data, shared with every reader: never mutate it. Write through `config_store.mutate` (as `/twitch-planning` does). An extension that keeps a load-time copy (`RELOAD_ON_SAVE`) takes `dict(...)` / `copy.deepcopy(...)` of it first. There is a single deployment, run by the maintainer, so there is no backward compatibility to keep: rename or restructure config paths and stored documents directly, with no startup migration, fallback or transition option, and list in the PR description what to change in `config.json` or the database.

## Notes

- **No URLs in the code**: user-facing links, icons, images and third-party endpoints belong in config, declared as a `ui(..., "url")` field on the module/section schema and read at use time — never hardcoded, not even as a schema `default`. An unset URL must degrade gracefully (omit the embed field, skip the task with a log line), not crash. A third-party API or site the whole bot shares goes in a global section named after the service, read at use time (`youtube`, `raiderio`, `zunivers`, `olympics`, `zevent`); a client in `features/` takes the base URL as an argument or a getter rather than reading the config itself (`ZuniversAPIClient(zunivers_api_url)`). Canonical URLs *derived* from data (`https://twitch.tv/{login}`, `https://youtu.be/{video_id}`, a Discord message jump link) are the exception, as are URLs derived from a configured one (Streamlabs' API, on the site of the guild's team URL). `tests/test_no_hardcoded_urls.py` fails on any other URL literal: a new canonical host goes in its `DERIVED_HOSTS`, with a reason.
