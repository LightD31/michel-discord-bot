# Logging and metrics

What is logged, reported and measured. Moved verbatim from `CLAUDE.md` (P12, D5); its one-line rules point here.

## Notes

- Logging: `from src.core import logging as logutil; logger = logutil.init_logger("name")`. `MICHEL_DEBUG=1` enables debug level, `MICHEL_LOG_FORMAT=json` one JSON object per line. Every record carries the log context (`src/core/log_context.py`: `correlation_id`, `guild_id`, `command`, `task`), bound for each command, button and modal by the client's `global_pre_run_callback` (`src/discord_ext/interaction_context.py`) and for each `Task` run by `src/discord_ext/task_health.py`. Background work started some other way can bind its own with `log_context.scope(...)`. Log an unexpected failure with `exc_info` (`logger.exception`, or `exc_info=e`): that is what the optional error reporting forwards (`src/core/error_reporting.py`, global section `errorReporting`, off without a DSN); an error line without one stays in the logs, as an expected failure. In an `except Exception`, use `log_failure(logger, msg, *args)` (`src/core/logging.py`): it attaches the traceback unless the error is an outage or a refusal (`is_expected_failure()` in `src/core/errors.py`: the bot's `DatabaseError` / `IntegrationError`, timeouts, connection errors, plus what `register_expected_failure()` adds: MongoDB connection failures, Spotify's transport errors, Discord's 403/404/429/5xx). `tests/test_failure_logging.py` fails on a plain `logger.error` in a broad `except`.

- **Prometheus metrics** (`extensions/metrics.py`, global section `metrics`): `/metrics` on its own port via `prometheus_client`, independent of the Web UI. Keep everything in the extension's own `CollectorRegistry` (never the global `REGISTRY`, which a reload would hit with duplicated series) and free the port in `async_drop`. Scrapes run on `prometheus_client`'s HTTP thread, so they only read the last snapshot published to `features.metrics.SnapshotCollector` plus plain client attributes; MongoDB is read only by the refresh task on the bot loop. Sample builders live in `features/metrics/samples.py` (pure, tested) — add a `MetricSpec` there for every new snapshot metric. Process health is recorded as it happens in `src/core/health.py` (framework-free, thread-safe): `Task` runs (`src/discord_ext/task_health.py` wraps `Task.__call__` / `Task.on_error` once in `main.py`, so no extension has to opt in), requests through the shared HTTP sessions (an aiohttp `TraceConfig` in `src/core/http.py`, one record per attempt), failed `spawn()` tasks and finished backups; `features/metrics/health.py` turns its snapshot into `michel_task_*`, `michel_http_requests_total`, `michel_background_task_failures_total` and `michel_backup_last_success_timestamp_seconds` at scrape time. A new periodic job gets those series for free if it is a `Task`; record anything else in `health` rather than in an extension-owned metric, so it is counted whether the exporter is on or not.

- **Incidents** (P21, `src/core/incidents.py`): an ERROR record whose log context holds a `guild_id` becomes one of that guild's last 50 incidents (reference, what, when, a French reason from the exception's type: `reason_of`, never its text), shown to its admins on the server page (`routes/incidents.py`, buttons named by their custom id's first word only, tasks by `TASK_LABELS`). Interactions bind `guild_id` already; a task looping over guilds binds it around each one (`with log_context.scope(guild_id=gid):`) so its failures land in the right server: `tests/test_incidents.py` fails on a `Task` loop over a module's `items()` / `guild_ids()`, `guilds` or the per-guild states that doesn't (loops over things several guilds share, a Twitch streamer or a vote, are listed in `NOT_PER_GUILD`). `log_failure` passes the exception as `record.failure`, so an expected failure without a traceback still gets its reason. In memory, gone at restart.
