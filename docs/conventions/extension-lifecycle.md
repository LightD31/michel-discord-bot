# Extensions: loading, reloading, commands

How an extension is loaded, reloaded from the dashboard, and how its commands reach Discord. Moved verbatim from `CLAUDE.md` (P12, D5); its one-line rules point here.

## Extension loading

`main.py` walks `extensions/` and loads every `.py` file or package. Enabled state comes from `config["extensions"]["extensions.<name>"]` (bool). Default behavior:

- Entries starting with `_` are disabled by default (none currently exist — `main.py` still honors the convention if you need to park work-in-progress code).

- All others are enabled by default. Several modules ship disabled in `config.example.json` instead (minecraft, olympics, speedons, zevent) — that's the normal way to disable, via config, not renaming.

- The Web UI writes to the same config key, so toggles persist across restarts.

`pyproject.toml` excludes `extensions/_*` from ruff and mypy.

`main.py` also runs a heartbeat task (touches `/tmp/bot_heartbeat` every 45 s while the Discord gateway still heartbeats, `gateway_alive()` in `src/discord_ext/lifecycle.py`) and a watchdog thread that exits the process when the heartbeat goes stale, so a wedged loop or a gateway stuck reconnecting gets restarted by `restart: unless-stopped` (the Docker healthcheck only reports, it restarts nothing). Don't remove or block either. SIGTERM / SIGINT (`docker compose stop`) go through `GracefulShutdown` (`src/discord_ext/lifecycle.py`): every loaded extension is released (Tasks stopped, `async_drop()` awaited), the shared HTTP and MongoDB clients are closed, the gateway is stopped and the process exits 0, within about 7 s or it exits anyway. A missing or token-less `config/config.json` stops startup with an explicit message. Gateway intents are enumerated explicitly in `main.py` — add the matching intent (with a comment) when a new extension listens to a new gateway event.

## Composition convention

When an extension grows past ~200 lines, promote it to a package and split responsibilities into mixin modules (e.g. `xp/leveling.py`, `xp/commands.py`, `xp/leaderboard.py`) composed via multiple inheritance in `__init__.py`. Shared constants and the Pydantic config schema go in `_common.py`. Domain logic moves into a matching `features/<name>/` package. A mixin declares what it uses from the extension class or a sibling mixin, so mypy can check it: class-level annotations for attributes (`bot: Client`), `if TYPE_CHECKING:` stubs for methods (`extensions/starboard/listeners.py`). A package whose mixins share much declares it once, in `_base.py` (a base every mixin derives from: annotations, and stubs under `TYPE_CHECKING`, so nothing exists at run time and the MRO is unchanged; `extensions/zevent/_base.py`). A stub for a method a mixin later in the MRO provides must sit under `TYPE_CHECKING`, or it shadows the real one. Every module is checked (P12, D4): no `ignore_errors` override, `tests/test_mypy_exclusions.py`. A guild command reads its guild with `guild_id_of(ctx)` (`src/discord_ext/messages.py`), not `ctx.guild_id`, which is typed `Snowflake | None`; likewise `guild_of(ctx)` for `ctx.guild`, `member_of(ctx)` for `ctx.author` (`Member | User`) and `message_of(ctx)` for a component's `ctx.message`, each raising on the bug where it is missing. An autocomplete's choices are `list[Choice]` (`src/discord_ext/autocomplete.py`).

## Web UI → bot dispatch

The dashboard serves requests from a daemon thread with its own uvicorn loop, so **never touch the running client inline in a route**. Anything that mutates the bot — `load_extension` / `unload_extension` / `reload_extension`, a command sync, sending a message — runs on the bot loop via `ctx.run_on_bot_loop(...)`, with the extension helpers in `src/webui/botops.py` (`run_extension_op`, `sync_commands`) as the entry points. Called inline, `reload_extension` makes interactions.py schedule its `synchronise_interactions()` task on the *uvicorn* loop while the client's aiohttp session belongs to the bot loop; the task dies with `RuntimeError: Timeout context manager should be used inside a task`, and since nobody awaits it the only trace is a stray "Task exception was never retrieved" while commands silently never sync. `run_extension_op` also suppresses the library's implicit per-call sync (one unawaited task per load *and* unload) — callers do one awaited `sync_commands()` when the command set actually changed. A route doing its own Discord work (list channels, post a role menu…) goes through `await ctx.call_bot(fn, what=...)`: a bounded timeout (504 when the bot doesn't answer), `HTTPException` passed through, anything else logged and turned into a generic 500. Never put `str(e)` in a response `detail`.

`run_extension_op` also completes the lifecycle the library's reload leaves half-done.

- **Before an unload or reload**, it stops every `Task` on the outgoing instance and awaits its optional `async def async_drop(self)`. It then purges the package's submodules from `sys.modules`, so `_common` and the mixins are re-imported (with the command scopes, and the settings of a `RELOAD_ON_SAVE` extension, read afresh). Without the purge, commands and tasks defined on cached mixins stay bound to the unloaded instance.

- **After a load or reload on a running client**, it runs the new instance's `on_startup` / `on_ready` listeners, because the gateway fires `Startup` / `Ready` only once per process.

So:

- Start background work from `@listen() async def on_startup` (idempotent: guard `Task.start()` with `if not task.running`, which `tests/test_task_start_guard.py` checks), not from `__init__`. A startup step that can fail (a MongoDB read) must not stand between the listener and its `Task.start()` calls: `Startup` fires once per process, so tasks skipped then never run. Load per-guild state on first use instead (Spotify's `ensure_state()`), and let each repository call raise `DatabaseError` rather than switch a feature off with a "database down" flag that nothing turns back on.

- Release anything that isn't a `Task` (a websocket, a socket.io client, a listening port, a third-party API client) in `async_drop`. `twitch`, `streamlabs` and `metrics` are the examples. The same `release()` runs on an unload and at process shutdown.

- Never re-implement reload handling inside an extension.

## Notes

- **Config-defined slash commands**: `extensions/customcommands` turns each guild's `moduleCustomCommands.commands` list into real guild-scoped `interactions.SlashCommand` objects — no command name is hardcoded. Register them from `async_start` (runs once every other extension is loaded, before the first command sync) or immediately in `__init__` when the bot is already ready (a dashboard reload never fires `async_start` again), append them to `self._commands` so `Extension.drop()` unregisters them, and never claim a name already in `bot.interactions_by_scope` — `add_interaction` raises on a duplicate. The extension declares `RELOAD_ON_SAVE`, so the dashboard save path (`src/webui/routes/servers.py`) reloads it and then syncs that one guild scope on the bot loop, so a new command reaches Discord without a restart.

- **Slash command scopes**: a module's commands exist only on the guilds where the module is enabled. Pass `scopes=guild_scopes(MODULE.guild_ids())` (`src.discord_ext.scopes`) to every `@slash_command` / `SlashCommand`, never the raw list: interactions.py turns an empty `scopes` into a *global* command (`scopes or [GLOBAL_SCOPE]`), so a module enabled nowhere would show on every server. Whole-bot maintenance commands go on the dev guild (`guild_scopes([devGuildId])`, like `/sauvegarde`). Right-click menus (`message_context_menu` / `user_context_menu`) are scoped the same way, and each carries `@menu_help("…")` above it (`src/discord_ext/menus.py`): Discord gives a menu no description, so that line is what `/aide` lists under the module, with where to find it ("clic droit sur un message → Applications"); `tests/test_help_command.py` fails on a menu without one, and on more than 5 message or 5 user menus (Discord's cap per server). A menu for moderators sets `default_member_permissions` and checks the right again when it runs, like a command. Six exist: 🚩 Signaler, ⏰ Me le rappeler, 💡 En faire une suggestion, ⭐ Mettre au starboard (messages), 🛡️ Historique, ⚠️ Avertir… (members). The only global commands are `random_`, `/aide` (guild-only through `contexts=[GUILD]`: it opens on what each server has, read from `bot.interactions_by_scope`, one entry per module under its dashboard label or the extension's `HELP_LABEL`, and a list to open a module's page: the `__help__` of its schema or the extension's `HELP`, both a `ModuleHelp` from `src/webui/schemas.py`; `/aide recherche:` lists matching commands) and `/mes-donnees` (a member's own data on every server, also in DMs); `tests/test_command_scopes.py` fails on any other unscoped command, and on a guild command declaring a user install, which Discord ignores there (`/sondage` and `/ping` did). compareai's `/ask` / `/ask-stats` are guild commands of the servers where the AI module is on (they were user-installable: anyone could spend the shared LLM budget, and `/ask` read channel history where no admin had enabled it). Every AI answer still passes `features/ai/quota.py` first: the kill switch, the module check, then a daily call reservation in `features/ai/usage.py` that fails closed. The dashboard keeps Discord in step: toggling a module, or a save that flips its `enabled`, reloads every loaded extension that declares the module in `MODULE_KEYS` (skipping ones disabled in the extension list) and syncs that guild's commands; any other save reloads only the extensions declaring `RELOAD_ON_SAVE`.

- Several extensions are tied to dated events (olympics → Milan-Cortina 2026, speedons → 2025 API slug). They ship config-disabled rather than deleted. `zevent` is no longer year-pinned: it resolves the edition from the stats API's `/events` listing (override with `zeventStatsEventId`), so only the two start dates need refreshing each year (global section `zevent`, read when the extension loads: reload it after a change).
