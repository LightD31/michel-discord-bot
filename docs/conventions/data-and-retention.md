# Data: storage, dates, retention

How state is stored and changed, and how long it is kept. Moved verbatim from `CLAUDE.md` (P12, D5); its one-line rules point here.

## Notes

- **Dates**: an instant the bot keeps (a deadline, a creation date) is an aware UTC `datetime` from `clock.now()` (`src/core/clock.py`), and MongoDB hands dates back aware in UTC (`tz_aware` client). An hour a member types and a daily schedule are wall times in `clock.LOCAL_TZ` (Europe/Paris): build them with `clock.at_local(day, hour, minute)`, read the current one with `clock.local_now()`, and step a recurrence on the wall clock (`clock.local_step`, `features/reminders/schedule.py`) so a 20:00 reminder stays at 20:00 across a daylight saving change. Use `zoneinfo`, never `pytz`; `tests/test_datetimes.py` fails on a naive `datetime.now()`, `utcnow()`, `date.today()` or `fromtimestamp()` without a zone. A birth date is a calendar day, stored at 00:00 UTC and never converted.

- **Backups** (`MongoManager.backup_all`) write one gzip-compressed Canonical Extended JSON Lines file per collection plus a `manifest.json` (`src/core/backup_format.py`, shared with `scripts/restore_backup.py`), streamed in batches on worker threads, into `<timestamp>.partial` renamed once complete, folders `0700` and files `0600` (`make_private_dir` / `open_private`). The retention counts and deletes only complete backups (`is_backup_folder`), never another folder under `backupDir`. Change the on-disk layout only together with the restore script and its round-trip test (`tests/test_backup_restore.py`). Operating procedures (restore, off-site copy, incidents, secret rotation) live in `docs/RUNBOOK.md`.

- **Change stored state in one update, never by writing back a copy.** Reading a document, editing it in memory and saving it whole (`$set` of every field, or a loop that upserts every document of a collection) drops whatever another click, task or thread wrote in between, and can resurrect what was just closed or deleted. Express the change as the update itself, filtered on the state it requires: `$push` / `$pull` / `$addToSet` / `$unset` on one field, a pipeline update for "append unless present" (`PollRepository.add_to_ranking`), `"closed": False` / `"is_drawn": {"$ne": True}` in the filter so a late vote or join changes nothing, and `find_one_and_update(..., return_document=AFTER)` when the caller needs the result (Secret Santa's `add_participant`, Spotify's `save_addwithvote_vote`). Write a session's progress before the step that can fail after it (the Spotify daily vote records its closing before opening the next one). Each such method gets a `mongo` test with concurrent calls.

- **Retention.** What the bot stores is kept only as long as something reads it, and `Privacy.md` §7 says how long: keep the two in step. XP events older than 400 days are folded into monthly totals per member and source (`XpRepository.archive_old_events`, daily; `xp_monthly`), the all-time totals per source are counters `log_event` keeps (`xp_totals`), and a guild's database and its `servers.<id>` settings are deleted 30 days after the bot leaves it (`extensions/datapurge.py`, `global.guild_purges`; a guild seen again cancels it). That purge and `/twitch-planning` are the only config writes the bot makes on its own. A member's data follows the same rules, by member (`features/userdata/`, `extensions/mydata.py`): `/mes-donnees exporter` sends them a JSON of everything stored about them, and `/mes-donnees supprimer`, on every server, and the daily purge 30 days after they leave one (`global.member_purges`, cancelled by `MemberAdd`), delete what is theirs alone, anonymise what others share (author ids become `NOBODY`, their votes stay counted under a key naming nobody) and keep moderation records, Secret Santa draws already made and Tricount while a balance is open. **A new collection holding a member id gets its line in `features/userdata/repository.py`**, deleted, anonymised or kept, with a `mongo` test, and `Privacy.md` says which. An extension that keeps member data in memory and saves it whole (ZUnivers' reminders) registers a forget hook (`register_forget_hook`) so the deletion goes through its state rather than being overwritten at its next save.

- **Stored keys are values, not field names**, when users choose them: a YouTube handle can contain a dot, which an update would read as a nested path (`features/youtube/repository.py` stores a list of `{"handle", "video_id"}` pairs for that reason). Interpolate a key into a field path only when it can't contain `.` or start with `$` (a Discord id, checked with `isdigit()` as in `SuggestionsRepository.toggle_vote`).
