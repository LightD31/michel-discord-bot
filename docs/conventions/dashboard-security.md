# Dashboard: authorization and saves

Who may do what in the dashboard, and the checks every save goes through. Moved verbatim from `CLAUDE.md` (P12, D5); its one-line rules point here.

## Web UI authorization

Three tiers, enforced via helpers on `WebUIContext` (`src/webui/context.py`): any authenticated Discord user has their own member space on the guilds they are a member of (`require_guild_member()`, below), and can manage the guilds where they hold `MANAGE_GUILD`/`ADMINISTRATOR` (or ownership); user IDs in `config.webui.developerUserIds` additionally get global config, extension reload, and the live log stream (the list is read at every check, `configured_developer_ids()` in `src/webui/auth.py`, so removing an id revokes it at once). Use `await ctx.require_guild_admin()` for per-guild routes, `await ctx.require_guild_member()` for a member's own data on a guild, and `require_developer()` for global ones — never skip the check. The auth endpoints are rate-limited per client IP (`src/webui/ratelimit.py`), and every mutating `/api/` request (`POST`/`PUT`/`PATCH`/`DELETE`) per session (`src/webui/mutation_limit.py`, 30 a minute; the template preview, sent as an admin types, has a budget of its own). Those requests, and `/auth/logout`, must also come from the dashboard's own pages (`src/webui/request_guard.py`): `Sec-Fetch-Site` `same-origin`, else an `Origin` naming the request's own host, or a 403; `SameSite=Lax` alone doesn't stop a neighbouring subdomain, and the body-less POSTs have no JSON content type to lean on. Forwarding headers are believed only from `webui.trustedProxies`, which defaults to loopback alone: a reverse proxy in a container or on another host must be listed (with the compose file, the project network's gateway), and the first forwarding header from an unknown peer logs a warning naming it.

- **Per-guild checks are live.** `require_guild_admin()` is async: it reads the member through the bot (`src/webui/guild_access.py`, cached 60 s), never trusting the OAuth guild list captured at login, so a demoted or banned member loses access within a minute. When the bot can't answer, the check fails closed (503). Only a dashboard with no bot client at all falls back to the login snapshot. It also answers 404 to an id not spelled the one canonical way (`is_guild_id()`: no leading zero, sign or whitespace): the path id becomes a config key and a database name, so `0123` would otherwise be a second copy of guild `123` that passes `int()`-based checks. `is_admin_user()` / `require_admin()` still read the snapshot and only gate endpoints with nothing guild-specific (module list, schemas).

- **The member space** (P10, C6, `src/webui/routes/me.py`, page `js/pages/me.js`, `#/me/<id>`): a member who manages no server lands on "Mon espace" instead of a dead end; admins have it in the sidebar too. For each server they share with Michel it shows their XP card, reminders, birthday, Tricount balances and Secret Santa wish list (`src/webui/member_space.py`, each section only where its module is on, `SECTIONS`), and lets them create, edit and delete a reminder, set their birthday, mark a Tricount debt paid ("J'ai remboursé": the payer is the member, and the line must be in the group's settlement plan as the page showed it, else 409) and edit their wish list until the draw, plus `/mes-donnees` (export, delete) for every server. Its tier is `await ctx.require_guild_member(request, guild_id)`: the canonical id check, then a live membership read (`guild_access().is_member`, cached a minute, fail closed; developers get no pass; the login snapshot only without a bot client). **A member-space route acts on `session.user_id` alone**: no path parameter or body field names a member (`tests/test_webui_member_space.py` checks every route), each write is filtered on the member in its repository (`ReminderRepository.update_mine` / `delete_mine`, `BirthdayRepository.set_own`), and `tests/test_mongo_member_space.py` seeds a second member's data next to the first's for every route. Its writes are not audited (the audit log is what admins change) and go through the mutation limiter. A new section gets a reader in `member_space.py`, an entry in `SECTIONS`, routes behind `require_guild_member()` and a `mongo` test with another member's data.

- **Sessions** live 24 h server-side, the same as their cookie (`SESSION_TTL_SECONDS` in `src/webui/auth.py`), and are keyed in memory and in MongoDB (`src/webui/sessions.py`, TTL index) by the SHA-256 of the cookie value, never the cookie itself. The OAuth tokens are used once at login and dropped. Any Discord account can log in, so a session keeps only the user's guilds the bot is in, with `GUILD_FIELDS`, and a user's oldest session is evicted beyond `MAX_SESSIONS_PER_USER` (5). The live log stream re-checks its viewer every 30 s (`src/webui/sse/logs.py`) and closes once they are no longer a developer or logged in. Logout is `POST /auth/logout`, so another site can't trigger it with a link. `global.webui_sessions` is excluded from backups (`BACKUP_EXCLUDED_GLOBAL_COLLECTIONS` in `src/core/db.py`).

- **The dashboard bar (`MANAGE_GUILD`) grants no Discord power by itself.** A route that makes the bot act with its own permissions on someone's behalf must apply the Discord rule the user would face by hand. The reference is role menus: `features/reactionroles/permissions.py` refuses staff roles outright (re-checked on every click) and requires `MANAGE_ROLES` plus a higher role from whoever builds the menu. The raw permission bits live in `src/core/permissions.py`.
  - **Roles in module settings follow the same rules.** Every `role` field (and a `keyvaluemap` of roles) declares what the bot does with it, `ui(..., role_use=…)` (`schemas.ROLE_USES`; `tests/test_module_registry.py` fails on a role field without one): `grant` (the bot hands it out: XP rewards, the birthday role; `grant_refusal`), `mention` (it pings it: mentionable, or the editor holds `MENTION_EVERYONE`), `access` (its holders get something outside Discord, LLDAP groups: `MANAGE_ROLES` and a higher role), `staff` (no check beyond the bar). A widget whose entries name roles lists them in `schemas.NESTED_ROLE_KEYS` with their uses (a streamer's or YouTube channel's mention role is checked as `mention` and `grant`, since its 🔔 button hands it out; a custom command's roles as `staff`), and `role_refs()` reads them like any other. The module save route checks the roles a save *adds* on the bot loop (`src/discord_ext/role_grants.py`) and answers 422; a save adding a text with `@everyone` / `@here` needs `MENTION_EVERYONE` too. The bot re-checks a configured role each time it grants one (`grantable_role()` / `auto_grant_refusal()`), and the LLDAP sync and `/inscription` never touch LLDAP's built-in groups (`lldap_admin`, `lldap_password_manager`, `lldap_strict_readonly`).
  - Revoking a sanction (`routes/moderation.py`) needs `MODERATE_MEMBERS`, read live, and refuses a case aimed at the revoker.
  - Slash commands that make the bot post in a channel the author picks check the author there with `author_can(ctx, channel, CAN_SEND)` (`src/discord_ext/messages.py`; `CAN_PIN`, `CAN_MANAGE`, `CAN_PURGE` likewise): `default_member_permissions` is only checked in the channel the command is run from. A command acting for a whole group or server checks its author at run time, not only through `default_member_permissions`, which a server can loosen (`/zevent-fin`, the Secret Santa exclusions, Tricount's group creator); one acting for the whole bot from the dev guild checks `configured_developer_ids()` (`/nextvote`). A default permission names the one permission the command needs (`slash_default_member_permission(Permissions.MANAGE_MESSAGES)`): Discord reads several flags as "all of them" and administrators pass every check, so `ADMINISTRATOR | MANAGE_MESSAGES` hid `/effacer` from every moderator, and from their `/aide` (`tests/test_default_permissions.py`).

- **A guild's settings stay in that guild.** `bot.fetch_channel()` (and the cache's `bot.get_channel()`) answers for every guild the bot is in, so every channel the bot looks up for a guild, an id from its settings or one the bot stored there, is resolved with `fetch_guild_channel(bot, guild_id, channel_id)` (`src/discord_ext/channels.py`), which refuses another guild's channel; `Guild.fetch_channel()` is limited to its guild already. `tests/test_channel_lookups.py` fails on any other lookup. It answers `None` for a missing, unreadable or foreign channel; with `raise_outages=True`, Discord not answering raises instead, for a caller that must not take an outage for a deleted channel (a poll or giveaway closing without its results, Spotify's add-with-vote). The module save route also checks every channel id the save *adds* (fields of type `channel`, plus the per-entry keys in `schemas.NESTED_CHANNEL_KEYS` for `rssfeedmap`, `streamermap` and `teams`) against the guild, on the bot loop, and answers 422 for a foreign or unknown one. A new widget type whose entries carry a channel gets a line in that table. A `channel` field the bot only links to (the welcome's "📜 Règles" button) declares `ui(..., linked_only=True)`: the save still checks it, the health card doesn't ask for the rights to post there.

- **Module saves** (`PUT …/modules/{module_name}` and `…/toggle`) only accept registered module names, and cap one module's config at 256 KB.

- **Saves are validated against the schemas.** `SchemaBase` is `extra="forbid"`, and the module and global-section save routes run `schemas.validation_errors()` inside the `mutate_config` mutator, so a 422 leaves `config.json` untouched; a global section must be registered (404 otherwise). The field annotation is the contract: it must match what the SPA sends for that widget type (e.g. `spotifymap` is a list, `messagelist` is `list[WeightedMessage]`). Type what the SPA writes back into its markup: an untyped `list[dict]` let a string reach a `value="…"` attribute. `schemas.config_problems()` runs the same check over a whole `config.json`: `scripts/check_config.py` prints it, and `main.py` logs it as warnings once the extensions are loaded (the bot starts anyway).

- **Security headers** (`src/webui/security_headers.py`, pure ASGI middleware): no framing, `nosniff`, `Referrer-Policy: same-origin` (public dashboard tokens sit in the URL path), HSTS when the request really came over HTTPS, and a Content-Security-Policy whose `script-src` is the dashboard's own files plus the pinned Chart.js build: no inline `<script>`, no `on…=` handler, no `eval`. So the SPA never writes `onclick="…"`: a control names an action, `data-click="saveShortLink" data-click-args="${actionArgs(code)}"` (`data-change`, `data-input`, `data-mousedown`, `data-keydown` likewise), and one delegated listener per event calls it from the `ACTIONS` allowlist (`js/core/actions.js`), which each module fills with its own: `registerActions({ saveShortLink, … })` at its end; `EL`, `CHECKED`, `VALUE`, `EVENT` and `dataArg()` stand for the element, its state and the event, and `data-prevent` (or a `false` return) cancels the default. A new action goes in its module's `registerActions`; `tests/test_spa_csp.py` fails on an inline handler or an action missing from the allowlist. Styles may stay inline (`style-src 'unsafe-inline'`), images come from any HTTPS host, requests only from the dashboard itself. Chart.js is allowed by its exact URL (`CHARTJS_URL`), also loaded with its SRI digest: bump both with the SPA's `CHARTJS_SRC`.

The one deliberate exception is `routes/public.py`: the per-guild public XP and Spotify dashboards (SPA pages at `/public/{token}/{xp|spotify}`). `token` is a random per-guild secret (`servers.<id>.publicDashboardToken`, minted and rotated by guild admins through `POST /api/servers/{id}/public-dashboard` and `…/rotate`), never the guild id, which every member can see. The pages are opt-in per module through the `publicDashboard` flag (`src/webui/public_links.py`), answer a bad token and an unpublished page with the same 404, strip Discord ids from their payloads (names only), hide the open Spotify poll's tally and voter names until it closes (the voter count may show), and cache each aggregation for 5 minutes so anonymous traffic can't hammer MongoDB. Keep all of these properties if you add another public page.

## Web UI config I/O rules

- **Mutations**: use `ctx.mutate_config(mutator)` — an atomic read-modify-write under the config write lock — never `get_full_config()` + `save_config()` in sequence (that pattern silently drops concurrent edits). Include the acting user (`session.username`/`session.user_id` from the `require_*` helper) in the mutation log line, and record the action in the audit log with `await audit.record(guild_id, session, "<area>.<verb>", target=…, changes=…)` (`src/webui/audit.py`; `guild_id=None` for an action on the whole bot): a guild's log is shown to every admin of that guild on its server page, the bot's to developers on the global settings page. `changes` holds field names (`audit.changed_fields(before, after)`), never values, so no secret or personal data is copied there; entries expire after a year (TTL). Recording never fails the request. A new action gets a French label in `AUDIT_ACTIONS` (`js/pages/audit.js`).

- **Secrets**: schema fields declared `secret=True` are masked to a placeholder in every API response (`src/webui/secrets.py`); the save paths call `restore_section()` so an untouched placeholder keeps the on-disk value. A secret declares where it is sent with `secret_field(…, sent_to=("lldapUrl", …))`: when a save changes one of those fields, the placeholder is refused (422) and the secret must be typed again, so a co-admin can't re-point a stored password at their own host. Every per-guild module secret declares it (`tests/test_module_registry.py`). Any new endpoint that returns config must mask (`mask_full_config` / `mask_section` / `mask_server_config`), and any new save path for schema-backed config must restore.

- **OAuth flows** (Spotify, Twitch; `src/webui/oauth_flow.py`): a server's account is connected by that server's admins (Spotify, P36: the state starts with the guild id, and the callback runs `require_guild_admin` for it again), the bot's own account by developers (Twitch). `…/auth/start` redirects with a random `state` kept ten minutes in an `HttpOnly`, `SameSite=Lax` cookie (`Secure` behind HTTPS), `…/auth/callback` compares it in constant time before exchanging the code, and answers with a page whose link back carries the outcome only (`…_auth=ok|error`), never a text. The callback URL is `webui.baseUrl` + the route, the value the service's console must list. Each server's Spotify token is written `0600` to `data/spotify/<guild>.json`. The bot's Twitch token (EventSub, Streamlabs' live status) is connected this way (`routes/twitch.py`, `src/integrations/twitch_auth.py`): written `0600` to `data/twitchcreds.json`, the file twitchAPI's `UserAuthenticationStorageHelper` reads, and the extensions using it reloaded. They bind it with `refuse_browser_login`, so a missing token is `TwitchNotConnected`, never a login server waiting on the container.

- **An outage is the app's answer** (P31, `src/webui/errors.py`): a route lets a `DatabaseError` go (MongoDB down, or no `mongodb.url`, which `MongoManager` raises as one too), and the app answers 503 with one French sentence, the driver's text in the logs only; anything else unexpected is the generic French 500. A route catches `DatabaseError` itself only where it can still answer without the database (the member space's overview, the health card, the server overview: each part `null` or "unavailable" in place). A test building its own `FastAPI()` calls `install_error_handlers(app)`.

- **Copying a module from another server** (P35, `src/webui/module_copy.py`, `routes/module_copy.py`): the editor manages both servers, read live; the source's settings are read on the server and never sent to the page. What names a guild's objects (`channel`, `forum`, `role`, `member` fields, their lists, the maps of roles or members, the per-entry keys of `NESTED_CHANNEL_KEYS` / `NESTED_ROLE_KEYS`) and the module's switch stay the target's; the answer lists what the target must fill. Secrets go only for the source's owner or an administrator there, read live like the Santa reveal; otherwise the target keeps its own secrets *and* the fields they are `sent_to`, so a copy never points the target's key at the source's host. The save is `save_module_settings(..., action="module.copy")`: checks, history, audit.
